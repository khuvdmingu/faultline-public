# 데이터 생성 정책

작성일: 2026-09-27 · 적용: Faultline 의 모든 합성 데이터 (Phase 0) 와 실데이터 전환 (Phase 1)

이 정책은 **합성 데이터를 어떻게 만들고, 어디까지 믿고, 무엇에 쓰지 않는가**를 정한다. 수치 규칙은 `engine/qa.py` 가 자동으로 검사한다. 정책의 숫자를 바꾸면 그 파일도 함께 고친다.

## 1. 원칙

1. **합성 데이터는 시험 도구지 증거가 아니다.** 합성 원문에서 나온 tension 이나 시나리오는 "사람들이 실제로 이렇게 행동한다"는 근거가 될 수 없다.
2. **정답을 먼저 심는다.** 데이터를 먼저 만들고 나중에 해석하지 않는다. 정답표 → 원문 순서로 만들어야 파이프라인이 정답을 되찾았는지 셀 수 있다.
3. **만드는 쪽과 읽는 쪽을 가른다.** 생성 모델과 해석 모델이 같으면 자기가 넣은 구조를 쉽게 되찾아 점수가 부풀려진다.
4. **쉬운 데이터로 얻은 통과는 통과가 아니다.** 함정과 거친 문체를 강제하고, 품질 검사 결과를 채점과 함께 읽는다.
5. **합성 표시는 지워지지 않는다.** 합성 원문에서 파생된 모든 레코드는 끝까지 `is_synthetic: true` 다.

## 2. 정답표 설계 (`hidden/ground_truth.json`)

| 항목 | 규칙 |
|---|---|
| tension 수 | 5~6개 |
| 두 극 | `pole_a` 와 `pole_b` 가 모두 있어야 한다. 한쪽짜리("정보를 좋아한다")는 tension 이 아니다 |
| 낯선 tension | **3분의 1 이상**을 `familiarity: "unfamiliar"` 로 둔다. LLM 이 익히 아는 것만 넣으면 사전 지식으로 맞힌 것과 구분이 안 된다 |
| principle | tension 마다 한 문장. 기능명이 아니라 원리 |
| 행동 씨앗 | tension 마다 3~5개. 생성 모델이 변주할 출발점이다. 원문에 그대로 쓰이면 안 된다 |
| 서로 겹침 | 두 tension 의 극이 같은 욕구를 가리키지 않게 한다. 겹치면 "재발견"을 판정할 수 없다 |
| 방해물 주제 | 5개 이상. 어떤 tension 에도 속하지 않는 행동의 재료 (기기 불만·가격·잡담 등) |
| 금지 | 실존 인물, 회사 내부 정보, 사용자 개인정보, `ref/`·`01_Profile/` 의 내용 |

정답표는 파이프라인이 볼 수 없는 `hidden/` 에 둔다. 파이프라인이 보는 탐색 과제는 따로 `brief.json` 에 쓰고, 여기에는 **정답 tension 을 적지 않는다.**

## 3. 함정 분류

원문 하나하나에 role 을 붙인다. 각 role 은 특정 지표를 시험한다.

| role | 수 | 무엇인가 | 시험하는 지표 |
|---|---|---|---|
| member | tension 당 8~12 (쌍둥이·함정 포함) | 그 tension 의 한쪽 극이나 충돌을 보여주는 행동 | tension_recall |
| distractor | 15~20 (역할 수. 무소속 전체는 false_friend·함정이 더해져 더 많다) | 어떤 tension 에도 속하지 않는 행동 | distractor_intrusion |
| twin | 5쌍 | 기존 member 와 같은 행동을 전혀 다른 어휘로 | twin_merge |
| false_friend | 5 | 어떤 tension 과 단어가 겹치지만 실제로는 다르다 | false_friend_split |
| counterexample | tension 당 1 | 그 tension 의 가정을 뒤집는 사람 | counterexample_kept |
| trap_negation | 3~4 | 부정·회피가 핵심인 문장 | negation_flip |
| trap_no_context | 3~4 | 기기·동반자가 드러나지 않는 문장 | hallucinated_context |
| trap_injection | 3 | 분석기에 대한 지시가 섞인 문장 (토큰을 심는다) | injection_leak |

함정 원문도 tension 을 가질 수 있다. 예를 들어 부정문이면서 HT_01 의 member 일 수 있다.

## 4. 문체와 현실성

LLM 이 만든 문장은 동기를 친절하게 설명해 실제 댓글보다 쉽다. 이를 줄이려고 분포를 강제한다.

| 문체 | 기준 |
|---|---|
| 짧고 동기 없음 (`short_no_motive`) | 40% 이상 |
| 속어·축약·오타 (`slang`) | 20% 이상 |
| 동기를 설명하는 긴 문장 (`long_motive`) | 25% 이하 |
| 반어·비꼼 (`sarcasm`) | 5% 이상 |

추가 규칙: tension 의 극 문장이나 씨앗 문장을 그대로 쓰지 않는다. 정답 ID(`HT_`)가 원문에 나오면 안 된다. 원문 ID 는 role 별로 몰지 말고 섞인 순서로 붙인다.

## 5. 라벨

라벨은 원문과 함께 생성되고 `split` 이 떼어 `hidden/labels.json` 으로 옮긴다.

| 필드 | 뜻 |
|---|---|
| `tension` | 속한 정답 tension. 무소속이면 null |
| `role` | §3 의 8종 |
| `twin_of` | 쌍둥이의 짝 (같은 tension) |
| `looks_like` | 거짓 친구가 겉보기로 닮은 tension (실제와 달라야 한다) |
| `expected_kind` | 추출돼야 할 주된 행동 종류 |
| `context_absent` | 원문에 드러나지 않는 맥락 필드 — 추출이 채우면 날조로 센다. 장면·기기·사람·앱이 글자로 나오면 넣지 않는다(2026-09-28: 날조 판정 37건 중 15건이 원문에 글자 그대로 있는 값 — 라벨 오류. 채점은 이를 `hallucinated_context_literal` 로 따로 보고하고 판정은 바꾸지 않는다) |
| `injection_token` | 주입 함정에 심은 대문자 토큰 — 파이프라인 산출물에 나오면 누출 |

## 6. 모델·세션 분리

- **생성 모델 ≠ 연결 모델 (필수).** 기본 배정은 생성 sonnet, 연결 opus.
- **생성 모델 ≠ 추출 모델 (권장).** 기본값은 둘 다 sonnet 이지만 세션은 분리돼 있다. 결과가 너무 좋으면 추출을 haiku 로 바꿔 다시 돌려 본다.
- 생성은 새 세션, 도구 없이. 채팅에서 돌린다면 메모리·이전 대화 참조를 끈다.
- 파이프라인 세션에는 정답표·이 정책서·원 설계 문서·대표 사례(스포일러 방지 등)를 넣지 않는다. 대표 사례는 정답 principle 을 가르쳐 준다.
- `claude_cli` 실행기는 이를 구조적으로 지킨다 (워크스페이스 밖 빈 폴더, 도구 없음). 수동 실행은 사람이 지켜야 한다.

## 7. 생성 후 검수

`split` 을 돌리면 `qa` 가 자동으로 검사하고 결과를 `runs/qa/corpus_qa.json` 에 남긴다.

| 판정 | 뜻 | 할 일 |
|---|---|---|
| 통과 | 모든 검사 PASS | 진행 |
| 주의 | WARN 만 있음 (예: 씨앗 문장 재사용, role 순서가 덜 섞임) | 진행하되 채점을 읽을 때 함께 본다 |
| 재생성 권장 | FAIL 이 있음 (수량·문체·극 문장 누출·구조 오류) | 새 실험으로 다시 생성한다 |

자동 검사 뒤에 사람이 무작위 20개를 읽는다. 확인할 것: 한국어 온라인 말투로 자연스러운가, 라벨이 문장과 맞는가, 거짓 친구가 정말 헷갈리게 생겼는가.

## 8. 버전과 재생성

- 한 실험 폴더(`experiments/<id>/`) = 정답표 한 판 + corpus 한 판. **파이프라인을 돌린 뒤에는 corpus 를 고치지 않는다.** 고치려면 새 실험 ID 로 만든다 (예: `tv-v1` → `tv-v2`).
- 같은 corpus 로 파이프라인을 2회 이상 돌려 점수 편차를 본다. 편차가 크면 한 번의 점수는 믿지 않는다.
- 모든 작업은 `runs/jobs/` 에 프롬프트·원본 출력·모델·시각이 남는다. 재현은 이 기록으로 한다.
- 정답표를 바꾼 이유는 `brief.json` 의 `note` 가 아니라 실험 폴더의 README 나 작업 기록에 남긴다 (brief 는 파이프라인이 읽는다).

## 9. 금지

- 실제 사람의 댓글·게시글을 복사해 "합성"으로 표시하지 않는다. 실데이터는 §11 절차로만 들어온다.
- 회사 내부 자료, 미공개 제품 정보, 사용자 개인정보를 정답표·brief·원문에 넣지 않는다.
- 합성 원문을 외부 서비스에 공개 데이터셋처럼 올리지 않는다.
- 결과를 보고 정답표나 채점 기준을 바꾸지 않는다. 기준은 실행 전에 고정한다 (`docs/PHASE0_PLAN.md`).

## 10. 합성 표시와 승격 금지

- `is_synthetic` 은 시스템이 부여한다. 모델 출력의 값은 무시한다.
- 합성 실험에서 나온 principle·시나리오를 실데이터 실험의 지식 기반에 옮기지 않는다. 옮겨야 한다면 `generated` 로 표시하고, 근거로 쓰지 않는다 (설계 §8.3 의 자기순환 방지).
- 사람이 합성 시나리오를 "발전"으로 골랐어도 그것은 **디자이너의 판단**이지 행동 증거가 아니다.

## 11. 실데이터로 넘어갈 때 (Phase 1)

1. 새 실험 폴더를 만든다. 합성과 실데이터를 한 실험에 섞지 않는다.
2. `data/raw/raw.jsonl` 에 원문을 넣는다. 필수: `is_synthetic: false`, 출처(URL 또는 식별자), 수집일, 자료 유형, 언어. 원문 수를 독립 사용자 수로 세지 않는다 (설계 §10.5).
3. 실데이터에는 정답 라벨이 없으므로 Phase 0 채점(90)은 돌지 않는다. 대신 추출 결과 20~30개를 원문과 직접 대조하고, 검토 결정과 후반 지표로 본다.
4. 핵심 비교는 **C(실데이터) vs C′(같은 크기의 합성 corpus) vs B(방법론 프롬프트만)**. C′ 와 차이가 없으면 수집 파이프라인의 추가 가치가 입증되지 않은 것이다.
5. 개인정보: 작성자 식별자는 저장하지 않거나 익명화한다.
