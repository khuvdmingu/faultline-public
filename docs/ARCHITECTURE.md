# 전체 구조와 로직

작성일: 2026-09-27 · 갱신: 2026-09-28 · 대상: Faultline v0.4 (Phase 0 — 합성 데이터로 연결 로직 검증)

이 문서는 Faultline이 **무엇을 어떤 순서로, 어떤 규칙 아래에서** 처리하는지 설명한다. 스테이지 목록 자체의 단일 출처는 코드(`engine/registry.py`)다. 웹의 구조도는 그 파일에서 그려지므로 이 문서와 그림이 어긋나면 코드가 맞다.

## 1. 한 문장

현실(지금은 합성)의 행동 원문에서 **행동 → tension → 원리 → 미래 가정 → 시나리오**로 이어지는 사슬을 만들고, 모든 고리가 원문까지 추적되게 남기며, 사람이 그중 발전시킬 것을 고르게 하는 시스템이다. Phase 0 에서는 정답을 미리 심어둔 합성 데이터로 **사슬의 앞부분(추출·연결)이 제대로 도는지**를 채점한다.

## 1.1 동작 원리 한눈에

한 번의 자동 실행(`faultline auto`)은 아래 순서로 돈다. 사람은 처음에 **탐색 과제(brief)** 만 적고, 끝에서 원하면 후보를 검토한다.

```text
 brief (기기·영역·기반 기술)
   │
   ├─▶ 00 정답표 ── 숨은 tension 4~6개를 심는다 (평가자 영역, 파이프라인은 못 봄)
   │     └─▶ 01 합성 생성 ── 정답에서 거꾸로 행동 원문을 만든다 (함정·방해물·쌍둥이·거짓 친구 포함)
   │           └─▶ 02 라벨 분리·품질 검사 ── 라벨은 hidden/ 으로, 원문만 data/ 로
   │
   ├─▶ 05 기준선 ── corpus 없이 만든 "뻔한" 시나리오 (나란히 돈다)
   │
   └─ 파이프라인 (정답을 모른다) ────────────────────────────────────────────────
        10 행동 추출 → 20 tension 연결 → [22 판단 필터] → 25 유추 → 27 검색 패키지
        → 30 principle → 35 미래 가정 → 40 시나리오 → 50 평가 ∥ 60 family
        → 75 후보 추리기 → 70 윤문 (후보만)
   │
   └─▶ 90 채점 ── 파이프라인이 심어둔 구조(20 연결까지)를 되찾았는가 · 표본 크기 n 표시
```

원리는 네 가지다.

1. **정답을 심고 되찾게 한다.** 실데이터에는 정답이 없어서 연결 로직이 맞는지 알 수 없다. 그래서 먼저 정답(tension)을 심은 합성 원문으로 "추출·연결이 구조를 되찾는가"를 잰다(Phase 0). 함정 8종(부정문·맥락 없음·지시문 주입·방해물·쌍둥이·거짓 친구·반례 등)이 흔한 실패를 일부러 유도한다.
2. **정답을 볼 수 없게 막는다.** 채점이 의미 있으려면 파이프라인이 정답을 읽을 수 없어야 한다 — 선언 검사·읽기 차단·실행 격리·화면 분리의 네 겹(§5).
3. **모든 고리가 원문까지 추적된다.** 시나리오 → principle → tension → 행동 → 원문 인용이 ID 로만 이어지고, 끊기면 검증이 잡는다(§4). 모델 출력은 저장 전에 검사한다.
4. **판단은 사람 몫, 추리기는 기계 몫.** 평가는 총점 없이 7~8개 차원으로 매기고, 후보 추리기가 규칙대로 5개를 고른다. 무엇을 발전시킬지는 사람이 블라인드 검토로 정한다(선택).

한 번에 걸리는 시간(2026-09-28 실측): quick(tension 4 · 원문 약 45 · 전 단계 sonnet · 짧게 쓰기) **11~13분**, standard(tension 6 · 원문 약 100 · 연결·원리·시나리오 opus · 짧게 쓰기) **약 15분**(판단 필터를 켜면 +6.5분). 시간은 (LLM 호출 수 ÷ 동시 실행 수) × 호출 길이로 정해지고, 그것을 줄이는 장치는 §9.4.


진입점은 세 가지다: 웹(`sh faultline serve --open` 또는 `Faultline.app`), CLI(`sh faultline auto|new|list|history|pool|score …`), 판단 모듈 CLI(`python3 -m judge …`). 셋 다 같은 엔진을 쓴다.

외부 네트워크 호출은 두 가지뿐이다. 브라우저가 디자인 시스템 CSS 를 CDN 에서 받는 것, 그리고 `claude_cli` 실행기를 켰을 때 claude CLI 가 모델을 호출하는 것.

## 4. 데이터 흐름과 계약

모든 엔티티는 JSONL 한 파일이고 ID 접두어로 종류가 드러난다 (`docs/SCHEMA.md`). 사슬은 ID 참조로만 이어진다.

```text
RAW ──source_id── BEH ──member_ids── TEN ──tension_ids── PRI ──principle_ids── PREM
                   │                  │                   │                     │
                   └──evidence_ids────┴──tension_ids──── SCN ──premise_ids──────┘
                                                          │
                                         EVAL(scenario_id) · FAM(scenario_ids) · DEC(scenario_id)
```

- 참조가 끊기면 `schema` 가 오류로 잡는다. 시나리오의 근거가 연결된 tension 밖에서 왔으면 경고한다.
- 행동의 `source_excerpt` 는 원문의 연속 부분 문자열이어야 한다 (공백 차이만 허용). 이것이 grounding 의 최소 조건이다.
- 모델이 매긴 ID 는 믿지 않는다. 작업을 마감할 때 시스템이 접두어 순서대로 다시 번호를 매긴다 (배치끼리 겹치지 않게).
- `is_synthetic` 은 모델이 아니라 시스템이 부여한다. 합성 실험에서 나온 모든 파생물은 `true` 이고, 검사가 이를 강제한다 (승격 금지).

## 5. 정보 차단선

Phase 0 채점이 의미 있으려면 파이프라인이 정답을 볼 수 없어야 한다. 네 겹으로 막는다.

1. **선언 검사** — `registry.check_barrier()` 가 모듈을 불러올 때 돈다. `hidden=False` 인 스테이지가 hidden 키를 입력으로 선언하면 서버가 뜨지 않는다.
2. **읽기 검사** — 프롬프트 조립은 `store.read(allow_hidden=False)` 로만 읽고, 선언되지 않은 키를 읽으려 하면 `BarrierError` 가 난다. API 는 이를 403 으로 돌려준다.
3. **실행 격리** — `claude_cli` 는 도구 없이(`--tools ""`), 프로젝트 밖의 빈 임시 폴더에서, 세션 저장 없이 실행된다. 기본 시스템 프롬프트는 짧은 작업자 지시로 교체하고(`--system-prompt`), 사용자 설정(`--setting-sources ""`)과 자동 메모리를 끈다. 모델은 프롬프트 본문 외에는 아무것도 읽을 수 없고, 상위 폴더의 CLAUDE.md·사용자 메모리도 붙지 않는다. (2026-09-27 실측: 임시 폴더만으로는 부족했다 — 사용자 메모리 안내가 붙어 모델이 데이터 대신 도구 호출문을 출력했다. 01 생성 결과는 이제 저장 전에 구조 검사를 거친다.)
4. **화면 분리** — 정답 라벨·채점·품질 검사는 API 에 `evaluator=1` 을 줄 때만 응답에 실린다. 블라인드 검토 중에는 평가자 모드를 끈다.

hidden 을 읽는 스테이지는 01 생성·02 분리·90 채점 셋뿐이고, 셋 다 평가자 층에 있다.

## 6. 실행 모델

### 작업(job)

LLM 스테이지 한 번 실행 = 작업 하나. `runs/jobs/<작업 ID>/` 에 모든 것이 남는다.

```text
생성   prompts.build → 배치별 프롬프트 파일 저장 (batch_00.prompt.md …)
채우기 claude_cli: 워커 스레드가 배치를 parallel 개씩 동시에 호출 → batch_00.out.txt
       (호출 시간 제한 quick 300초·standard 600초, 일시 오류·시간 초과는 15초 뒤 한 번 재시도)
       manual:     사람이 배치별로 복사 → 채팅/서브에이전트 실행 → 붙여넣기
마감   파싱(코드 펜스·설명 줄 무시) → 병합 → ID 재번호 → is_synthetic 부여 → 스키마 검사
       통과: 저장 (직전 판은 .prev 로 1개 보관) + runs/provenance.jsonl 에 한 줄
       실패: rejected.jsonl 로만 남기고 상태 needs_review — 사람이 「오류를 알고도 저장」할지 결정
```

상태: `waiting`(수동 대기) · `queued` · `running` · `done` · `failed` · `needs_review`. 작업 워커는 2개, 한 작업 안의 배치는 `parallel` 개씩 동시에 돈다(§9.4). 서버가 재시작되면 돌던 작업은 `failed` 로 표시되고 재시도할 수 있다 — 단 작업에 적힌 소유 `pid` 가 살아 있으면(터미널의 `faultline auto` 가 돌리는 중) 건드리지 않는다.

저장은 전부 원자적이다(`store.atomic_json`: 임시 파일에 다 쓴 뒤 `os.replace`). 병렬 배치가 `job.json` 을 쓰는 동안 다른 배치·폴링이 반쯤 쓴 파일을 읽어 `JSONDecodeError` 로 멈춘 적이 있다(phone-agent-v1 첫 실행).

### 실행기

| 실행기 | 언제 | 과금 |
|---|---|---|
| manual | 항상 가능. 채팅·서브에이전트에서 돌린다 | 쓰는 도구의 플랜 |
| claude_cli | `claude` 로그인이 살아 있을 때. 상태는 `/api/executors` 가 haiku 한 번으로 확인(5분 캐시) | claude.ai 구독 로그인이면 플랜 사용량. `ANTHROPIC_API_KEY` 가 있으면 API 과금 가능 — 경고 표시 |

데스크톱 앱 안에서 서버를 띄우면 부모 세션의 환경변수가 상속돼 CLI 인증이 꼬일 수 있다. 실행기는 이 변수들을 떼고 호출한다.

### 결정적 스테이지

`split`(02) · `package`(27) 은 LLM 없이 즉시 돈다. 채점(90)과 커버리지는 저장된 산출물에서 매번 다시 계산한다.

## 7. 검색 패키지 (retrieval_v01)

설계 §15 의 60/20/20 을 출발점 가설로 구현했다. 최적값이 아니다.

- **relevant** — 그 tension 의 member 행동 (최대 12).
- **adjacent** — 다른 tension 소속이거나 무소속인 행동 중, 같은 감상 단계를 공유하거나 표현이 가까운 것 (최대 4). 선택 이유를 `reasons` 에 남긴다.
- **distant** — 그 tension 의 유추 + **다른 tension 의 먼(distant) 유추** 1개 이상 (최대 4). 뒤의 것은 결정적 해시로 고른 "뜻밖의 연결"이다.
- 반례는 비율과 별도로 항상 넣는다.

principle(30)은 패키지를, scenario(40)는 principle 이 가리키는 tension 의 근거만 evidence 로 쓸 수 있다. 인접 행동은 영감용이며 근거가 되지 못한다.

## 8. 검증의 세 겹

| 겹 | 무엇을 | 언제 | 정답 필요 |
|---|---|---|---|
| schema | 형식·ID·참조·원문 인용·합성 표시 | 작업 마감마다, 화면을 열 때마다 | 아니오 |
| qa | 합성 corpus 가 정책을 지켰는가 (수량·문체·누출·구조) | 02 분리 때 | 예 (평가자) |
| scoring | 파이프라인이 심어둔 구조를 되찾았는가 | 90 채점 | 예 (평가자) |

qa 가 FAIL 인 corpus 로 얻은 채점 PASS 는 믿기 어렵다. 쉬운 데이터에서 통과한 것일 수 있기 때문이다. 채점 화면은 둘을 나란히 보여준다.

후반 스테이지(유추·가정·평가·family)에는 정답이 없다. 여기는 구조 검사와 사람의 검토로 본다. 후반 지표(평가 커버리지·뻔함 비율·발전 수율·독립 family 수율)는 정답 없이 계산한다.

## 9. 인간 검토

설계 §22.3 을 따른다. 블라인드 모드에서는 ID·평가 점수·family·horizon 을 숨기고, 실험별로 고정된 무작위 순서로 보여준다. 먼저 설명만 보고 판단한 뒤 근거를 연다. 결정(발전·보류·거절)에는 이유가 필수이고, 블라인드 여부와 근거를 봤는지가 함께 기록된다. 결정은 추가만 하고 고치지 않는다. 같은 시나리오를 다시 판단하면 최신 결정이 유효하다.

### 9.1 윤문 (70)

사람이 읽는 문장(시나리오 제목·상황·경험·가정·실패 장면, principle 문장, 미래 가정)에서 AI 티를 덜어낸다. 규칙과 사후 검사는 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)(MIT, `vendor/im-not-ai/VENDOR.md`)를 쓴다.

- 규칙은 두 층이다. 먼저 **Faultline 문체 규칙(F-1~F-5, 시나리오만)**, 다음 im-not-ai quick-rules. F 규칙이 따로 있는 이유: im-not-ai 는 번역투·피동·상투구를 잡는데, 시나리오가 기계처럼 읽히는 원인은 주로 경험 문단 끝의 정리 문장, 반복되는 "사용자" 주어, 결과를 나열한 실패 장면이었다(tv-v1 에서 im-not-ai 진단 = risk low). F-1 은 정리 문장을 지우지 않고 새 필드 `takeaway`(화면의 「핵심」)로 옮긴다 — 해석은 남고 본문은 장면으로 끝난다.
- 모델은 두 규칙표에 걸리는 구간만 고치고, 의미·수치·고유명사·서법(당위·추측)·문체를 유지한다. 입력 안의 지시문은 데이터로 다룬다.
- 저장 전에 레코드마다 `verify_gates.py` 를 코드로 돌린다. 변경률 30~50% 또는 서법·수치 이상은 `warned`(채택하되 표시), 50% 이상은 `rejected`(원문 유지), 검사를 못 돌리면 `unchecked`(원문 유지).
- 원본 레코드는 바꾸지 않는다. 윤문본은 `data/polish/polished.jsonl` 에 따로 두고, 웹 상단의 「윤문본」 스위치로 덮어 보여 준다. 추적·평가·채점의 근거는 언제나 원본이다.
- 평가(50)보다 뒤에 둔 이유: 평가는 기준선(윤문 안 함)과 비교하므로, 시나리오만 윤문하면 문장 매끄러움이 새로움·뻔함 점수를 흔든다.

### 9.2 후보 추리기 (75) — 사람 없이 나오는 결과

`engine/steps.shortlist`. 근거·현실성 3 미만, 뻔함 4 이상, 평가 경로 reject, 추적 끊김을 먼저 뺀다. 남은 것의 점수 = 평균(근거·tension·새로움·현실성·기기 적합·에이전트 적합*) − 0.5×(뻔함−1) (*평가에 있을 때만). AI 필요성은 성격 정보라 점수에 넣지 않는다. 그다음 **tension 마다 하나**(한 문제에 몰리지 않게), 다음으로 family 마다 하나씩 골라 상위 5개를 이유와 함께 남긴다. 가중치는 출발점 가설이다 — 사람 검토가 쌓이면 이 순위와 대조해 고친다. 블라인드 검토 중에는 화면에서 자동 순위를 숨긴다.

### 9.3 자동 실행

`engine/runner.py`. 순서는 `AUTO` 목록 하나(00 → … → 70 → 75 → 90). 시작점을 주지 않으면 결과가 비어 있는 첫 단계부터 끝까지 돈다(그 뒤 단계는 앞 단계가 바뀌었으니 다시 만든다). 정답표가 이미 있으면 00 은 명시하지 않는 한 건너뛴다. LLM 단계는 작업 큐에 넣고 끝날 때까지 기다리며, 실패하면 한 번 재시도한다. 검증 오류(needs_review)·구조 오류가 나면 저장하지 않고 멈춘다. 기준선(05)은 처음부터 본 사슬과 나란히, 60 family 는 50 평가와 나란히 돈다. 품질 검사가 「재생성 권장」이면 01 생성을 한 번 다시 돈다. 상태는 `runs/autorun.json` 한 파일이고, 끝나거나 멈출 때마다 `runs/history/` 에 요약이 남는다(§9.8). 서버가 재시작되면 서버가 돌리던 실행은 interrupted 로 보인다. 새 실험은 `engine/experiments.create`(brief + 빈 hidden/·data/)로 만든다.

### 9.4 크기와 속도 (config.json)

실험 폴더의 `config.json` 한 파일(`engine/config.py`). 정답이 없는 설정이라 파이프라인이 봐도 된다.

| 크기 | tension | 합성 원문 | 기준선 | 모델 |
|---|---:|---:|---:|---|
| quick (빠르게) | 4 | 약 45 | 15 | 전 단계 sonnet |
| standard (표준) | 6 | 약 100 | 30 | 연결·원리·미래 가정·시나리오·윤문 opus |

시간은 (호출 수 ÷ 동시 실행 수) × 호출 길이로 정해진다. 그래서 세 가지를 쓴다.
- **배치 동시 실행** — 한 작업 안의 배치를 `parallel`(기본 3, 최대 6)개씩 동시에. 일시 실패는 15초 뒤 한 번 다시.
- **작업 워커 2개** — 자동 실행에서 기준선(05)을 처음에 띄워 본 사슬과 나란히 돌리고 평가(50) 직전에 기다린다. 60 family 는 시나리오·principle 만 읽으므로 50 평가를 시작할 때 함께 띄우고 자기 차례에 기다린다.
- **01 생성 분할** — tension 2개씩 배치 + 무소속·함정 배치 1개를 동시에. 합친 뒤 전체를 섞어 `RAW_001…` 로 다시 번호를 매긴다(배치마다 role 이 몰려 ID 순서가 정답을 흘리지 않게, `jobs._shuffle_corpus`). 정책의 「tension 당 소속 원문」은 member + 그 tension 에 달린 twin·함정의 합이다. 그래서 twin·부정문 함정이 붙을 tension 을 코드가 정해 배치에 적어 주고(맥락 없음·주입 함정은 무소속), member 는 tension 마다 (목표 − 그 몫) 개로 요청한다 — 이전에는 모델이 함정을 아무 tension 에나 달아 품질 검사가 매번 재생성을 권했다.
- **배치 고르게 나누기** — 배치 크기 = min(등록부 상한, ⌈항목 수 ÷ parallel⌉)(`prompts._even`). quick 추출 49행이 30+19(두 바퀴 몫) 대신 17·17·15 로 한 바퀴에 끝난다.
- **탐색 층 분할** — 25 유추는 tension 2개씩, 30 principle 은 패키지 3개씩 배치로 나눠 동시에(둘 다 「tension·패키지당 몇 개」 규칙이라 나눠도 결과가 같다). 35 미래 가정은 principle 끼리 엮는 일이라 한 배치로 둔다.

그 밖의 설정 (웹 파이프라인 탭 · CLI `--brevity --profile --polish --family`):

| 키 | 값 | 효과 |
|---|---|---|
| `brevity` | normal · **short** | short 면 텍스트를 만드는 단계(05·10·20·25·30·35·40·50·60) 프롬프트 끝에 길이 규칙을 붙인다(`prompts.SHORT_RULES`) — 출력이 짧아져 시간도 준다 |
| `profile` | **full** · check | check = 검증 전용: 00·01·02·10·20·90 만 (`runner.CHECK`). Phase 0 가 실제로 재는 구간이라 연결 로직을 고치며 반복할 때 쓴다 |
| `polish` | **shortlist** · all · off | 윤문 대상. shortlist 면 75 후보 추리기가 고른 시나리오만 (그래서 자동 실행 순서가 75 → 70) |
| `family` | **on** · off | off 면 60 을 건너뛴다. 후보 추리기는 tension 다양성으로 대신한다 |
| `baseline_split` | **off** · held · avoid | 기준선(05)을 반으로 나눈다(`prompts.baseline_halves`). held = 50 평가가 보관분(홀수 번째)으로만 뻔함을 잰다(대조군). avoid = 거기에 더해 40 시나리오가 나머지 절반을 「뻔한 방향」으로 보고 피한다. 평가가 시나리오가 본 목록과 비교하면 외운 목록을 피한 것만 재게 되므로 두 몫은 겹치지 않는다 |
| `assign` | **off** · on | on 이면 20 뒤에 22 판단 필터 B 를 돈다(check 흐름에도 들어간다). quick 기준 약 4분 추가 |

새 실험의 기본값은 웹 폼 기준 quick · short · full.

### 9.5 기반 기술 (brief.technology)

brief 의 `technology`(새 실험 기본값: 에이전틱 AI — 목표를 받아 스스로 계획하고, 여러 앱·기기에서 대신 행동하며, 필요한 순간에만 묻는 AI)가 있으면 **탐색·평가 층에만** 규칙을 덧붙인다(`prompts.TECH_RULES`). 증거 층(추출·연결)에는 붙이지 않는다 — 원문에서 행동과 욕구를 찾는 일은 기술 관점과 무관해야 하고, 그래야 Phase 0 점수가 기술 설정에 흔들리지 않는다.

- 30 principle: 이 기술로 새로 가능해지는 방향을 염두에 두되 기술 이름은 쓰지 않는다
- 35 미래 가정: 절반 이상은 이 기술이 보편화된 세계
- 40 시나리오: `agent_actions`(대신 하는 일) · `human_checkpoints`(사람에게 묻는 순간) · `reversal`(되돌리기·권한 회수) 필드를 더한다. 위임의 경계가 드러나게
- 50 평가: 차원 `agent_fit` 추가 → 75 후보 추리기 점수에 들어간다

### 9.6 판단 필터 B (22)

`engine/assign.py`. 판단 모듈의 assign 태스크(`judge/tasks.py`)를 20 연결의 tension 두 극만 후보로 삼아 돌리고(`judge/backends.ClaudeCliBackend`), 규칙 네 줄로 합친다: ① B 가 accept 한 행동은 B 의 답 ② review 는 20 연결 유지 ③ 20 연결이 반례로 둔 행동을 B 가 무소속이라 하면 반례 유지 ④ tension 은 버리지 않는다. 규칙은 phone-agent-v1 에서 B 단독을 본 뒤, **새 corpus 로 검증하기 전에** 고정했다(v1, 기본). 비교용 규칙 두 개가 더 있다(`config.assign_rule`): v2 = 연결 member 를 B 가 반례라 해도 유지(연결 단독과 같아져 채택 안 함), v3 = 같은 tension 에서 member → 반례면 빼기. 판단 한 번에 세 규칙의 결과를 모두 `judge_runs/<ID>/tensions.v1·v2·v3.jsonl` 로 저장한다. 오류가 판단의 절반을 넘으면(예: 사용 한도) tensions 를 바꾸지 않고 멈춘다. 판단 기록은 `judge_runs/<ID>/assign.jsonl`, 20 연결 원본은 `data/linked/tensions_link.jsonl`. 같은 실행 안에서 `faultline score --tensions data/linked/tensions_link.jsonl` 로 필터 전후를 비교할 수 있다. 정답표는 읽지 않는다.

### 9.7 표본 크기와 합산

판정마다 분모 `n` 이 붙고, 5 미만이면 「표본 작음」 표시가 붙는다(판정은 바꾸지 않는다 — 기준은 사전 고정). quick 은 부정문 함정 2 · 쌍둥이 3 · 거짓 친구 3 · 반례 4 라, 한 건이 판정을 뒤집는다(phone-agent-v2 의 negation_flip 0.50 은 2개 중 1개, 그 1개도 라벨이 애매했다). 그래서 quick 은 **속도·구조 확인용**이고, 연결 로직 판단은 standard 또는 `faultline pool`(여러 실험의 분자·분모 합산, 같은 기준) 로 한다. 합산은 각 실험의 현재 산출물로 다시 계산하므로 실험마다 설정(예: 판단 필터 on/off)이 다르면 그 차이가 섞인다.

### 9.8 실행 기록 (runs/history/)

자동 실행이 끝나거나 멈출 때마다 `engine/history.py` 가 요약 한 장을 `runs/history/<실행 ID>.json` 에 남긴다: 설정 · 스테이지별 시간과 행 수 · 산출물 수 · 레코드당 평균 글자 수(원칙·가정·시나리오 — 짧게 쓰기 효과 확인) · 이번 실행에서 채점했으면 판정(지표 이름·값·PASS/FAIL 만, 정답 내용 없음). 데이터 자체는 여전히 덮어쓴다(직전 1판 `.prev`). 보기: 파이프라인 탭 「실행 기록」 · `faultline history --root …` · `GET /api/history`.

크기는 정답표·원문을 새로 만들 때 적용된다. QA 수치(`qa.py`)와 정답표 검사도 같은 설정을 읽는다. 실측은 §13.

## 11. 확장 지점

- **새 스테이지** — `registry.STAGES` 에 한 줄, `prompts.build` 에 입력 조립 규칙, `prompts/` 에 템플릿, `schema.SPECS` 에 계약. 구조도는 자동으로 따라온다.
- **새 실행기** — `executors` 에 함수 하나와 `jobs._work` 분기. 예: 승인된 사내 모델, 로컬 모델. 출력 계약이 같으면 뒤 스테이지는 바뀌지 않는다.
- **판단 모듈 (`judge/`)** — 판단을 "상태 + 닫힌 질문 → 선택지별 확률"로 쪼개 Jev 로 교체할 수 있게 한 독립 패키지. 붙일 자리는 A(10 추출 뒤 검사) · B(20 연결 뒤 배정) · C(40 뒤 지도화). **B 는 22 판단 필터로 연결됐다**(§9.6, 백엔드 `claude_cli` — 외부 키 없음). Jev early access 가 열리면 `JevBackend._client` 를 채우고 백엔드 이름만 바꾼다. A 는 질문이 행동당 약 5개라 비용 추정이 먼저, C 는 Phase 1(실데이터)부터. 근거는 [JUDGE.md](JUDGE.md) §6·§8.
- **실데이터 (Phase 1)** — 새 실험 폴더를 만들고 `data/raw/raw.jsonl` 에 `is_synthetic: false` + 출처 메타데이터로 넣는다. 합성과 실데이터를 한 실험에 섞지 않는다 (데이터 생성 정책 §11).
- **A/B/C 비교** — 05 기준선이 조건 A 다. 조건 B(방법론 프롬프트만)와 C′(합성 corpus)는 같은 brief 로 실험 폴더를 나눠 만든다.

## 12. 알려진 한계

- 합성 데이터에서의 통과는 실데이터에서의 통과를 보장하지 않는다. 합성 문장은 실제 댓글보다 깔끔하다.
- 후반 스테이지의 품질(유추가 정말 같은 구조인가, 미래 가정이 의미 있는가)은 자동으로 채점되지 않는다.
- judge(50)의 점수는 보정된 확률이 아니다. 같은 후보를 다시 평가했을 때의 흔들림은 아직 재지 않았다 — 두 조건의 차이가 이 흔들림보다 작으면 구별이 안 된다(기준선 반 나누기 비교가 그 예).
- 22 판단 필터의 확률은 verbal(모델이 말로 적은 값)이라 보정이 가장 약한 방식이다. Jev·logprobs 백엔드와의 비교가 남았다.
- quick 한 판은 판정 10개 중 5개가 분모 5 미만이다(§9.7). 연결 로직의 좋고 나쁨은 standard 나 합산으로 판단한다.
- 합성 원문의 라벨도 틀린다 — 맥락 날조 판정의 약 40% 는 생성 라벨 오류였다(`hallucinated_context_literal`). 정답표가 서로 겹치는 tension 을 심은 적도 있다(watch-agent-v1).
- 사용량 한도: claude CLI 는 구독 플랜 사용량을 쓴다. 긴 자동 루프는 한도에 걸려 멈출 수 있고(2026-09-28 두 번), 멈추면 저장하지 않고 멈춘다 — 이어 돌리면 된다.
- 커버리지의 감상 단계는 추출이 채운 `context.phase` 에 의존한다. 원문에 단계가 없으면 「불명」이 많은 것이 정상이다.

## 13. 실험으로 확인한 것 (2026-09-28 기준)

실험은 전부 합성 데이터다. 자세한 수치·원인은 각 `experiments/<이름>/FINDINGS.md`.

| tv-v1 | AI TV · 콘텐츠 선택 | standard · 순차 | 36분 | 9/10 |
| familyhub-v1 | 냉장고 · 주방·가족 | standard | 22분 | 8/10 |
| phone-agent-v1 | 폰 · 일상 비서 에이전트 | quick·short | 16분 | 9/10 |
| phone-agent-v2 | 폰 · 이동·여행 | quick·short·필터 | 16.6분 | 8/10 |
| watch-agent-v1 | 워치 · 건강 조치 | quick·short | 13.8분 | 4/10 |

**연결 로직** — standard 크기 work-agent-v1 이 첫 10/10(표본 작음은 부정문 하나뿐). 9개 실험을 합쳐도(`faultline pool`) 지표 10개 모두 PASS 다. 실험별 FAIL 은 서로 다른 지표(반례 보존·거짓 친구·방해물 침입·tension 복원)에 흩어진다. 한 판의 FAIL 은 대부분 표본이 작은 지표다.

**22 판단 필터** — 규칙을 먼저 고정하고 새 corpus 6개에 적용했다. 20 연결 단독의 방해물 침입이 0.22 이상이었던 3개(watch·photo·shop)에서는 모두 좋아졌고(photo: tension 복원 0.25 → 0.75), 침입이 0 이던 2개(phone-agent-v2 · work-agent-v1)에서는 효과가 없거나 약간 나빴다. standard 에서는 108 판단에 391초로 가장 큰 단계가 된다. 효과는 "연결이 member 로 끌어들인 행동의 재분류"와 "연결이 놓친 행동 붙이기"에서 나온다. 라벨 없이 연결이 흐트러졌는지 알아챌 신호가 없어 기본값은 off.

**짧게 쓰기** — 시나리오 글자 −44%, principle −60% (phone-agent-v1 vs familyhub-v1). 에이전틱 필드가 붙고도 짧다.

**시도했으나 효과가 불분명한 것** — 기준선 반 나누기(1승 1패), 필터 규칙 v2(연결 단독과 같음), v3(v1 과 거의 같음). 코드와 기록은 남겨 두고 기본값은 바꾸지 않았다.

**측정 쪽 발견** — quick 은 표본이 작아 판정이 흔들린다 · 생성 라벨 오류가 날조 판정의 약 40% · 소속 원문 수가 정책과 어긋나 품질 검사가 매번 재생성을 권하던 문제는 twin·함정을 코드가 배정하면서 사라졌다.

**운영 원칙 (지킨 것)** — 같은 corpus 로 프롬프트를 고치고 재채점하지 않는다: 모든 수정은 다음 새 corpus 에서 확인했고, 규칙 비교는 corpus 를 보기 전에 규칙을 고정했다. 이미 본 corpus 에 새 규칙을 적용한 값은 "사후 참고"로만 적었다.
